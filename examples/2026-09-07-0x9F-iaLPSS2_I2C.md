# Case 2026-09-07 — 0x9F DRIVER_POWER_STATE_FAILURE (Intel I2C controller)

A real, complete run of this skill. Demonstrates why `!analyze -v`'s bucket
module (here `pci.sys`) is often NOT the real culprit on 0x9F, and how
`!devobj` / `!irp` find the driver that actually blocked the power IRP.

## Crash info

| Item | Value |
|---|---|
| Time | 2026-09-07 20:07 local |
| Event | BugCheck 1001 + Kernel-Power 41 |
| Stop code | `0x0000009f` |
| Args | `(0x3, 0xffffb507a20c2360, 0xffffd70dea25f790, 0xffffb507ab1d3a10)` |
| Dump | `C:\windows\Minidump\090726-7843-01.dmp` |
| Context | Normal desktop use, no sleep/shutdown involved — device idle D-state transition |

Arg decode for 0x9F with P1=3 ("a device object blocked a power IRP too long"):
P2 = device object (feed to `!devobj`), P4 = the blocked IRP (feed to `!irp`).

## `!analyze -v` key fields

- `BUGCHECK_CODE: 9f`
- `FAILURE_BUCKET_ID: 0x9F_3_ACPI_IMAGE_pci.sys`
- `STACK_TEXT` includes `nt!PopIrpWatchdogBugcheck` → confirms the power-IRP
  watchdog fired (driver didn't complete a power IRP in time)

Note the bucket blames `pci.sys` — an image-name artifact, not actionable.

## Going deeper: `!devobj` / `!irp`

Key findings from the cdb session (summarized, not raw output):

- `!devobj ffffb507a20c2360` → device sits on an ACPI stack.
- `!irp ffffb507ab1d3a10` → blocked IRP is `IRP_MN_SET_POWER`; the current (`>`)
  stack location shows `pending` at `\Driver\ACPI`, and the lower stack entry
  belongs to `\Driver\iaLPSS2_I2C_ADL` — the Intel Alder Lake PCH I2C
  controller driver that never completed its part of the power transition.

→ Real culprit: **`iaLPSS2_I2C_ADL.sys` (Intel chipset I2C controller
driver)**, not `pci.sys`, not ACPI itself.

Caveat: Windows "kernel generated triage dumps" may not support `!devobj` /
`!irp` (registers + stacks only). If the commands fail, say so in the report
and fall back to the bucket + stack interpretation — don't guess.

## Conclusion (plain language)

The Intel I2C controller driver hung during a routine device power-state
transition (device going idle). Windows waited, gave up, and bugchecked.
**Driver/software issue — not a hardware failure.** Repeat of the same 0x9F
signature on 2026-08-02 confirmed a pattern.

## Fixes applied

1. Update the Intel chipset driver (covers `iaLPSS2_I2C_ADL`) from the board
   vendor — root-cause fix.
2. Mitigation with user consent: `powercfg /h off` + Sleep/Hibernate "Never"
   in the power plan (note: disabling Fast Startup alone is NOT equivalent).
3. Exclude `C:\Windows\Minidump` from Storage Sense cleanup so future dumps
   survive long enough to analyze (this very case's dump was later deleted
   by Windows cleanup — see SKILL.md Step 2).
